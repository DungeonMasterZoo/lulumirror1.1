# USB access and backup research

> This is a chronological research record. Statements about status and untested steps describe the time they were written, not necessarily the current state. Read the later entries and the [project overview](../README.md) before acting.

## Development setup

On Apple Silicon macOS, install [mise](https://mise.jdx.dev/getting-started.html) and Apple's command-line developer tools. From the repository root, review `mise.toml`, then run:

```sh
mise trust
mise install
mise run setup
```

`mise install` provides Python 3.15.2, UUU 1.5.243, Android platform-tools 37.0.2, xPack AArch64 GCC 15.2.1-1.1, and Pixi. `mise run setup` installs the locked project-local dependencies. Version pins alone do not guarantee byte-identical builds. The shim package and custom U-Boot configuration remain unvalidated on hardware, as described below.

These mise-managed tools were installed and their executables checked on Apple Silicon macOS. UUU's read-only device listing ran successfully, and the extraction script verified its existing outputs under mise-managed Python. No MIRROR was detected during that check, so it was not a device communication test.

The NXP macOS UUU binary contains hard-coded Homebrew library paths. To avoid relying on them, use `mise run usb` or `mise run uuu -- <arguments>`: the UUU task sets `DYLD_LIBRARY_PATH` to the locked project-local Pixi libraries. A macOS dynamic-loader trace confirmed that OpenSSL, libusb, zstd, and tinyxml2 loaded from `.pixi/`, not Homebrew. Running bare `uuu` bypasses the task and may still require Homebrew. The USB task is read-only; other UUU arguments may write to hardware.

Use `mise run usb` for read-only device detection and `mise tasks` to list local preparation tasks. No mise task flashes the MIRROR. The UUU download currently targets Apple Silicon macOS; other platforms need equivalent tools separately.

`mise run spl-test -- --check` checks the reference SPL hash, local runtime libraries and command without contacting the device. `mise run spl-test` is different: it asks for `sudo` and executes the reference SPL in device RAM, with no flash command. Only run it after reviewing the risks and confirming the target; the reference SPL's compatibility is not established. Afterward, `mise run usb` checks for the SDPV mode transition. The hash identifies the downloaded reference file, not its authenticity or compatibility with a particular MIRROR.

With the device in SDPV mode, `mise run atf-test -- --check` verifies the reference ATF hash and shows its command without contacting the device. `mise run atf-test` writes that ATF to RAM at `0x00920000`, using `sudo`; it does not flash, jump, or load other components. It is not a full boot test and the reference ATF's compatibility is not established.

The separate `mise run tee-test` task writes the reference TEE into RAM at `0xbe000000`; `mise run tee-test -- --check` only validates its inputs and shows the command. It does not flash, jump, or verify hardware compatibility.

`mise run uboot-test` writes the specifically hash-pinned local research build `build/uboot-nxp-task.qsrMm7/u-boot.bin` into RAM at `0x40200000`. It does not flash, jump, or execute that image. This build is experimental and contains commands capable of writing storage. `mise run uboot-test -- --check` checks inputs without contacting the device. The task requires that exact local build path and refuses a different hash.

`mise run fdt-test` writes the reference device tree into RAM at `0x43000000`. The separate `--check` mode validates local inputs without contacting the device. Neither mode flashes or jumps.

`mise run shim-test` writes the exact hash-pinned local experimental package `build/shim-package.dvxmz4/shim.imx` into RAM at `0x40000000`; `--check` only validates local inputs. This task does not jump to it. The unsigned shim and its compatibility with the SPL remain unverified.

`mise run shim-jump` is a separate execution step: it requests sudo and sends `SDPV: jump -addr 0x40000000`, executing whatever shim is in RAM and attempting to start ATF, TEE and U-Boot. It cannot verify what is currently loaded, and it issues no flash command. The experimental U-Boot contains commands capable of writing storage and its behavior on this device is not established. `mise run shim-jump -- --check` only prints the command and checks local libraries.

Once fastboot appears, `mise run uboot-version` sends the fixed UUU command `FB: ucmd version` to ask the temporary U-Boot for its version; it does not issue a storage command. `mise run uboot-version -- --check` prints the command without contacting the device. This tests individual command dispatch and output, not an interactive serial prompt.

`mise run uboot-output` attempts to route the running U-Boot's stdout to `serial,fastboot` using `FB: ucmd setenv stdout serial,fastboot`. This changes the environment in RAM, does not call `saveenv`, and could disrupt the USB session. Its `--check` mode does not contact the device. Retry `mise run uboot-version` afterward to check whether output reaches the host.

### Backup preparation: identify storage

First keep the temporary U-Boot powered and check it is in fastboot with `mise run usb`. After enabling output using `mise run uboot-output` and verifying `mise run uboot-version`, run `mise run mmc-list` to list U-Boot's MMC devices. This sends only `FB: ucmd mmc list`, without a storage write, erase, or `saveenv`. `mise run mmc-list -- --check` checks the local command without contacting the device. Record and review the result before selecting a device: the guide's example `mmc 2` is not proof of the correct number on this unit. An MMC listing is not a backup. A read-and-transfer method and image verification are still required; never run a write or flash operation merely because a device appeared.

In the current temporary session, `mmc list` reported `FSL_SDHC: 1` and `FSL_SDHC: 2`. This identifies controllers, not which one contains the eMMC. In this NXP source, `mmc dev` calls the hardware-partition selection path, which issues an eMMC partition-access configuration command while preserving other configuration bits. Do not treat it as merely printing the current device or assume its effects without review. Neither controller has yet been confirmed as the eMMC.

`mise run mmc-inspect` selects MMC 2's user hardware partition and runs `mmc info` and `mmc part` in order, stopping on failure. Selection may update the hardware partition-access bits, as described above; this is not a purely passive query. It does not intentionally write disk blocks, erase, expose UMS, or save the U-Boot environment. `mise run mmc-inspect -- --check` only prints the commands and checks local dependencies. Compare the reported card type, capacities, and partition layout to the guide before treating MMC 2 as the target.

On this MIRROR, that inspection completed with MMC 2 selected as hardware partition 0. `mmc info` reported MMC 5.1, a 14.6 GiB user capacity, 4 MiB boot capacity, and 4 MiB RPMB capacity. `mmc part` reported 12 GPT entries; `boot_a` starts at LBA `0x8000` and has `0x20000` sectors, `boot_b` starts at `0x28000` and has `0x20000` sectors, and `super` starts at `0x4c000` and has `0xe00000` sectors. These three entries match the expected offsets and sizes in the upstream [flash tool](https://github.com/ikiiftekhar2/lemonademirror/blob/main/image/flash-mirror.py). This is a partial layout match, not a full execution of the installer's GPT checksum, content, image-size, or disk-identity checks, and it is not a backup.

Backup-method source review: despite `.config` showing `CONFIG_CMD_USB_MASS_STORAGE` unset, the legacy EVK header defines it and the linked U-Boot binary contains `do_usb_mass_storage` and `fsg_init`. The `ums` implementation wires its write callback to `blk_dwrite`, so it can expose a **writable** block device; do not launch it as a read-only backup method. It also changes USB gadget mode and could end the fastboot command session. NXP's fastboot upload implementation uses an internal received-byte counter and bounds uploads; the existence of `upload` alone does not establish a reliable whole-disk backup route. Neither method has been tested on this MIRROR. Source: [USB mass-storage command](https://github.com/nxp-imx/uboot-imx/blob/d26632454196662187c2562e404655fa88eea4cb/cmd/usb_mass_storage.c), [NXP fastboot commands](https://github.com/nxp-imx/uboot-imx/blob/d26632454196662187c2562e404655fa88eea4cb/drivers/fastboot/fb_fsl/fb_fsl_command.c).

#### User-area backup attempt (USB handoff untested)

1. First load the separate UMS-handoff U-Boot using the RAM-only boot sequence; `mise run uboot-ums-test` transfers the hash-pinned build but does not execute it. With that build in fastboot mode, `mise run backup-expose -- --check` prints the planned commands without contacting the device. `mise run backup-expose` temporarily routes output, checks the displayed `bootcmd`, restores stdout to serial, and requests `fastboot continue` for the observed MIRROR serial. The bootcmd check cannot prove which command is already executing. The task lists disks before and afterward, but an acknowledgment does not prove UMS started. This USB-only handoff has not been tested and may interrupt fastboot or require a power cycle. The exposed disk is **writable**; if macOS asks to initialize it, choose **Ignore**, never Initialize.
2. Identify the newly attached whole USB disk independently by its size and partitions. With all its volumes unmounted, run `mise run backup-copy -- diskN`, replacing `diskN` only after confirming the correct disk. The task refuses non-USB/internal/partition devices, mounted volumes, unexpected sizes, corrupt GPT checksums, and partition identifiers that differ from those observed on this MIRROR. These checks reduce, but cannot eliminate, the risk of selecting the wrong disk or a disk changing during a long copy.
3. After explicit confirmation, the task reads the source with `sudo dd if=/dev/rdiskN` and writes only to a new `~/Downloads/mirror-backup/mirror-user-area.img.partial`. It refuses existing output paths, requires available space, checks exact byte count, hashes the file and rereads and hashes the source, then creates `mirror-user-area.img` without overwriting an existing file. A failed copy or verification leaves the partial file for inspection. Do not modify the exposed disk while copying; this task cannot prevent macOS or another program from writing to a writable UMS device.
4. This copies only the **eMMC user area**, not hardware boot0, boot1, or RPMB. Make a second independent copy, and plan separate boot-partition backups; hash comparison does not demonstrate that restoration works.

The copy task's GPT validation has offline synthetic tests, but neither task has been tested against the live UMS disk. Do not use a disk identifier from an example without checking the currently connected device.

In the first USB-only UMS attempt, UUU acknowledged `FB: acmd ums 0 mmc 2`, but no new disk appeared and Android fastboot still detected the device. The acknowledgment alone does not establish that UMS started. Do not run the backup-copy task until an actual new disk is independently confirmed. The revised expose task reports failure when no new whole disk is immediately visible; enumeration could still be delayed, so inspect manually before retrying.

Source analysis suggests that starting UMS directly inside the fastboot callback attempts to register a second gadget while the first remains registered. As a local experiment, `mise run uboot-ums-build` builds a separate RAM-only U-Boot with `bootcmd=fastboot 0; ums 0 mmc 2`; the intended handoff is for the host to request fastboot `continue`, allowing fastboot's cleanup to finish before the boot command starts UMS. This approach is **untested**, and the resulting UMS is the ordinary writable implementation, not a write blocker. It has not been sent to the MIRROR. Testing it would require a new RAM boot; it may fail or require a power cycle. See [fastboot command cleanup](https://github.com/nxp-imx/uboot-imx/blob/d26632454196662187c2562e404655fa88eea4cb/cmd/fastboot.c) and [USB composite registration](https://github.com/nxp-imx/uboot-imx/blob/d26632454196662187c2562e404655fa88eea4cb/drivers/usb/gadget/composite.c).

The local handoff build at `build/uboot-nxp-task.9GbZRg/u-boot.bin` has SHA-256 `c59fe703096ad83d5f654753b58d9f07b4e2d51622bcc6247a44b1fe40825386`. The `uboot-ums-test` task refuses a different hash and only writes the file to RAM; execution remains a separate jump. The normal `uboot-test` task continues to select the previous fastboot-only build.

On the MIRROR, that build reached fastboot and reported the expected `bootcmd`. The host's `fastboot continue` returned `OKAY`, but no new disk appeared immediately or on a subsequent `diskutil list`. UUU still listed the gadget by its fastboot VID/PID. A non-sudo `fastboot getvar version` then failed with a USB pipe error, so it did not establish whether fastboot remains responsive. The transition to UMS remains unproven; no user-area backup was created.

A subsequent sudo-based `FB: ucmd version` failed with `LIBUSB_ERROR_IO`; the current fastboot session is not responding to that command. A simpler local-only experiment, `mise run uboot-direct-ums-build`, builds an untested RAM U-Boot whose default command is `ums 0 mmc 2`, avoiding an in-session fastboot-to-UMS transition. Its UMS implementation is ordinary **writable** UMS, and the image does not automatically provide a fastboot command interface. Building it does not send it to the MIRROR; testing it would require another RAM boot and would attempt to expose the writable disk immediately. The actual transition and backup remain unverified.

The first direct-UMS build was `build/uboot-nxp-task.oxKMNW/u-boot.bin`, SHA-256 `838282e12839c2dcca14824f292ff4c51065cca1faf36ba5f6d84cd08e6f9138`. Its hardware attempt did not expose a disk. `mise run ums-direct-boot -- --check` verifies the currently selected local inputs without contacting hardware. From a freshly powered-on SDP session, `mise run ums-direct-boot` runs the RAM-only sequence and then immediately attempts writable UMS after the shim jump. If macOS offers to initialize a disk, choose **Ignore**, never Initialize. It issues no intentional flash, erase, or saveenv command.

The first direct-UMS hardware attempt instead appeared as fastboot and no disk appeared. Source inspection found that NXP's `bootdelay_process()` overrides the configured command for USB boot, and can choose the manufacturing boot command, whose fallback is fastboot. Thus a matching compiled `bootcmd` string did not prove that UMS would run. A revised direct-UMS build applies `patches/uboot-direct-ums-usb-boot.patch` to an isolated source copy to bypass both USB-boot command overrides. This is an experimental target-code change, not a proven device fix; it does not affect the other build modes. The revised build is `build/uboot-nxp-task.LHWaKn/u-boot.bin`, SHA-256 `52b99eb75edeafa04691fba33913e2bbdf419926eeb19c72134f4a2ba9347c9b`. Its default UMS command and linked UMS handler are present, while the USB override log strings are absent. `ums-direct-boot` now selects this revised image; its hardware behavior is untested.

`mise run ums-boot -- --check` checks the exact SPL, ATF, TEE, UMS U-Boot, device-tree and shim inputs and prints their commands without contacting the device. From a freshly powered-on SDP session, `mise run ums-boot` runs those RAM transfers and the shim jump in order, stopping on failure. It executes experimental firmware and the UMS-handoff U-Boot, which may expose a writable disk when fastboot exits. It does not intentionally flash, erase, or save the environment. This complete sequence is untested; no hashes establish compatibility or prove RAM contents after transfer.

Before backup, select a destination with enough free space for the complete 14.6 GiB user area plus boot-partition images and verification overhead, preferably with room for a second independent copy. The workspace had approximately 14 GiB free at the time of inspection, insufficient for a complete uncompressed user-area image.
