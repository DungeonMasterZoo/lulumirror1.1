# Camera investigation

> This is a chronological research record. Statements about status and untested steps describe the time they were written, not necessarily the current state. Read the later entries and the [project overview](../README.md) before acting.

## Camera investigation

LemonadeMirror booted and SSH worked. Display test pattern worked. Camera probe failed with `ov5640 2-003c: failed to power on` and I2C register errors even after a physical power cycle and an explicit driver reprobe. `/dev/video10` was loopback output-only because `camhub` waited for the missing OV5640 media entity. The declared DTBO image in the user's backup matches the reference byte-for-byte (the remainder of the 4 MiB partition differs). No camera pin/clock/voltage changes were made.

The original vendor DTBO requests camera clock `IMX8MM_CLK_CLKO1` (clock id `0x9e`) at 24 MHz, while the LemonadeMirror source uses `IMX8MM_CLK_24M`, and labels clock and supply wiring borrowed. Its device tree assigns AVDD to LDO4, DOVDD to LDO3 and DVDD to BUCK5. On the running MIRROR regulator debugfs reported those rails at 1.5 V, 1.8 V and 1.8 V respectively, after the failed probe. Upstream OV5640 driver comments describe typical supplies as AVDD 2.8 V, DOVDD 1.8 V and DVDD 1.5 V. These are software descriptions/PMIC-reported values, not measurements of camera module pins; neither the board's physical rail mapping nor voltage during probe is established. The reference's clock difference and borrowed supplies are hypotheses, not proven causes. Do not adjust shared regulators or clock registers based only on these observations.

The NXP 5.4 OV5640 driver calls `clk_prepare_enable()` on its `csi_mclk` reference; the original DTBO names CLKO1 at 24 MHz. `mise run prepare-camera-clock-test` generated a local-only candidate `build/camera-clko1-test.dtb` SHA-256 `f1cd30738b28929c7385c9d72d3069201cccb1d97f10b73bb4787dafd02b27ef` from the pinned LemonadeMirror DTB, changing the camera's clock reference and assigned parent/rate while leaving its supplies alone. A decompile/recompile structural check passed. It has not been installed, booted, or verified to drive the sensor's physical clock input; no voltage mapping was established.

The installed `/dev/mmcblk2p4` `imx8mm-mirror.dtb` was inspected using a temporary read-only mount and SHA-256 matched the pinned original `1f0702287ff95611776b89f42c665684706ed8c025a9bb42292e4deffe15dc41`. A separate verified copy is `~/Downloads/mirror-backup/lemonademirror-original.dtb` on the Mac. The stock Android user-area image remains separately at `~/Downloads/mirror-backup/mirror-user-area.img`.

Recovery plan, not yet exercised end-to-end: if Linux and SSH still work, mount `/dev/mmcblk2p4` and restore the verified original to `imx8mm-mirror.dtb`, then unmount and reboot. If Linux cannot boot, power off, connect PROG1 as before, use `mise run ums-direct-boot`, choose Ignore on macOS, identify the new 15.7 GB MIRROR disk and its fourth FAT partition, and restore the verified original file to that partition. Confirm the whole-disk identity, partition, mount point and copy/read-back hashes before rebooting; disk numbers can change. This relies on the previously successful USB RAM-boot route, but restoring this specific file through it has not been tested. The preinstallation stock Android image is not a backup of the currently installed Debian boot partition.

`mise run test-camera-clock -- --check` verifies local test and recovery files without contacting the MIRROR. The live `mise run test-camera-clock` stages the untested DTB over SSH, requires a typed confirmation, verifies the current installed DTB, makes and verifies an `imx8mm-mirror.original.dtb` backup on the boot partition, installs and verifies the candidate, then unmounts. It changes the Linux boot partition but does not reboot. If any step fails, inspect the output before rebooting. The USB file-restore path is still not tested end-to-end.

The user ran the live task successfully: the original on the boot partition was backed up and the experimental candidate was installed and verified. After reboot, the live device tree contained CLKO1 and its 24 MHz assigned rate, but OV5640 still failed to power on with the same I2C errors. This does not establish whether a clock reached the camera physically. `mise run restore-camera-dtb -- --check` checks the restore task locally; live `mise run restore-camera-dtb` restores the verified original from the boot-partition backup over SSH, then verifies it. It does not reboot.

The user ran `mise run restore-camera-dtb` successfully; the original DTB on disk was restored and verified, and the MIRROR was subsequently rebooted.

After reboot with the original DTB, camera still failed. The kernel config has `CONFIG_FTRACE` and dynamic debug disabled, so I2C tracepoints were unavailable. A targeted bind of the unbound `ov5640` I2C device `2-003c` returned errno 6 (`ENXIO`); the matching NXP i.MX I2C driver uses this error for a missing acknowledgment. Together with the logged OV5640 register failures, that supports a bus non-acknowledgment during camera probe, not proof of which signal or component failed. The probe may toggle the sensor's power/reset controls; it did not intentionally alter storage or regulator voltage settings.

`mise run sample-camera-probe -- --check` checks the diagnostic locally; the live task samples debugfs GPIO 6/7 and oscillator/CLKO1 clock rows while retrying one unbound OV5640 driver bind over SSH. This triggers the driver's normal transient camera power/reset sequence but does not write boot files or change regulator voltage settings. Fast transitions may be missed and debugfs values are not physical measurements. The user ran it: bind returned ENXIO, sampling showed GPIO6 reset low then high and GPIO7 powerdown high then low, the `osc_24m` clock gained `2-003c` as an xclk consumer during the probe, and `clko1` remained unused under the restored original Linux DTB. Two such GPIO assertion/release sequences were observed within one bind interval; the cause of the repeated sequence is unconfirmed. The device remained unbound. These values show software state, not actual voltages or a clock waveform at the sensor.

The initial diagnostic used buffered Python text I/O for the sysfs bind. A local synthetic `OSError(ENXIO)` test of the same buffered I/O pattern attempted the raw write twice, so automatic retry during close is a plausible explanation for the two observed probes, though not proven on the MIRROR. The sampler now uses a single `os.write()` and no buffered retry; it has not been rerun. NXP's 5.4 driver holds powerdown low for 5 ms before releasing reset and waits 5 ms afterward, while upstream 6.18 requests at least 1 ms and 20 ms respectively. The sampled order was consistent with releasing powerdown before reset, but debugfs sampling cannot establish exact electrical timing. The original DTBO gives no camera supply phandles, so it does not validate LemonadeMirror's borrowed regulator-to-sensor mapping.

`mise run build-camera-timing` builds a local-only OV5640 module experiment using the project's pinned Linux 6.18.60 configuration, its patch set and an isolated Linux container. The experimental patch changes only the powerdown-to-reset delay from 1 ms minimum to 5 ms minimum, while retaining the existing post-reset delay. The build does not contact the MIRROR or install a module. It is untested and `modules_prepare` alone cannot establish full ABI compatibility; do not load the result before verifying compatibility and a rollback procedure.

The build succeeded at `build/camera-timing.Y8bzANnH/ov5640.ko`, SHA-256 `2f1fa8d0775cdf8da2b4600e4af4034ce1a3b5eb56e6baa62d9b71e93351f3d1`. Its architecture, vermagic (`6.18.60-dirty SMP preempt mod_unload aarch64`) and undefined-symbol names match the release module. The release module SHA-256 `e759349fd739e2d0f3151a5836ccdef03ce93ca0e1763f493424fdd11b3a8091` matches the MIRROR's installed file, and its required V4L2 dependencies were loaded at inspection. Because no complete Module.symvers was available, the experimental module has an empty `depends` metadata field, unlike the original, and these checks do not prove binary compatibility.

The user subsequently ran `mise run test-camera-timing`: the experimental module loaded, but the sensor did not bind and the same register errors appeared. Cleanup reported unloading the test module, reloading the original, verifying its on-disk hash, and restarting `camhub`. A later power cycle and hardware check still reported 19 of 20, camera failing.

A further offline comparison read the original Android `dtbo_a` from the user-area backup and decompiled its embedded tree, then compared it with the release Linux DTB. The camera powerdown group, reset/24 MHz pin group, and I2C3 pin group have identical raw `fsl,pins` values. Both describe GPIO1_IO7 as active-high powerdown and GPIO1_IO6 as active-low reset. Android requests CLKO1 at 24 MHz with the 24 MHz clock as parent, whereas the release Linux DTB requests the 24 MHz clock directly; the previous CLKO1 test changed the clock reference and assignments but kept these same pin groups and did not fix the probe. Identical configuration values do not establish the actual electrical direction or routing of the clock pin, or prove that any signal reaches the camera. Android's tree contains no sensor supply phandles. No device was contacted during this comparison.

An offline comparison of PMIC constraints found both trees declare BUCK1–6 and LDO1–4 boot-on and always-on. Android permits LDO3 and LDO4 from 0.8–3.3 V, while the Linux tree permits 1.5–3.3 V; Android permits LDO5 from 1.8–3.3 V, while Linux constrains it to 3.3 V and neither marks it always-on. Constraints are not measured voltages or proof of camera wiring. The public NXP `lf-5.4.y` OV5640 reference driver requests DOVDD, DVDD and AVDD regulators, but it has not been shown to be the exact vendor binary; the stock camera node has no corresponding supply phandles, so the reference source alone does not identify physical rails or actual Android regulator behavior. No regulator changes are justified by these differences. The backup's small metadata partition root was inspected read-only and did not reveal camera logs; userdata and Android logical partitions were not searched, so historical camera operation remains unknown.

The userdata filesystem was subsequently inspected by read-only, offset-based ext4 metadata reads without mounting or copying the partition. Its encryption feature is enabled and the `misc`, `vendor`, `tombstones`, `anr`, `system`, `bootchart` and `per_boot` directories have the ext4 encryption flag set. Their encrypted contents were not searched or decrypted, and no historical camera logs were established; Android logical partitions also remain unsearched. This does not mean logs are absent or the camera did not work under Android.

The Android `boot_a` kernel was extracted locally with `mise run extract-android-kernel` to `build/android-camera-analysis/android-boot-a-Image`, SHA-256 `0cfe944eb52bff8151001676365a29eb79bff0da21c170b48e490addc74cbda9`. It is an ARM64 Linux 5.4.47 image. A separate local Python 3.15.2 venv with `vmlinux-to-elf` 1.4.0, lz4 4.4.5, minilzo 1.2, zstandard 0.25.0 and peewee 4.5.3 reconstructed its kallsyms into `android-vmlinux.elf`. The tool warned about its base/offset heuristics; the recovered `tas5806_probe` address matches upstream's independently documented address and the camera function disassembly has coherent calls and strings, but this is not a full verification of the reconstruction. `aarch64-none-elf-objdump -d --start-address=0xffff800010d22448 --stop-address=0xffff800010d231dc build/android-camera-analysis/android-vmlinux.elf` produces the saved `ov5640-probe-reset-disassembly.txt`.

Unlike the generic NXP `lf-5.4.y` reference source previously examined, the stock binary's camera probe has two sensor-identification paths: it first drives powerdown to the low operational level and checks for ID 0x5640; on a failed first attempt it sets an internal flag, runs reset again with reversed powerdown levels and checks for ID 0x5645. This is a vendor-specific distinction and a possible lead, not proof this board has an OV5645 or reversed wiring. The first stock reset also drives reset high before asserting it low, then toggles powerdown, with waits; the upstream Linux module test changed only one delay and did not reproduce that whole sequence. The stock probe calls regulator_get for DOVDD, DVDD and AVDD and requests 1.8 V, 1.5 V and 2.8 V respectively, but the original camera node has no explicit supply phandles and the actual regulator resolution and physical wiring remain unknown. Do not apply these voltages to shared rails. No alternate polarity or reset sequence has been tested on the device.

`mise run build-camera-polarity` builds a local-only module changing the initial and subsequent physical powerdown GPIO levels, without the timing patch or regulator changes. The built test artifact is `build/camera-polarity.9LYH08NX/ov5640.ko`, SHA-256 `b1a7dda8f981be8bec43e524bb4714106ed294a5f9789087fe1a34cb17619cb4`. Its architecture, vermagic and undefined symbol names match the original module, but the missing full Module.symvers and empty dependency metadata mean ABI compatibility is unproven. `mise run test-camera-polarity -- --check` performs only local checks; the live task stops camhub, temporarily loads the experiment, checks binding, and attempts to restore the unchanged original and service. The polarity variant has not been run on the MIRROR. It tests polarity in the mainline OV5640 driver; it is not a full implementation of the original Android driver's OV5645 path.

The user subsequently ran the polarity test. The kernel reported `ov5640_check_chip_id: wrong chip identifier, expected 0x5640, got 0x5645`. Thus with reversed powerdown levels, the device responded over I2C and identified as 0x5645; the unmodified OV5640 identification check rejected it and the sensor did not bind. Cleanup reported removing the test, reloading the original module, confirming its file hash, and restarting camhub. This is strong evidence the sensor is OV5645 and the prior I2C failure was conditional on powerdown polarity; it does not yet demonstrate streaming or validate the complete OV5645 configuration. Do not simply bypass the ID check without researching sensor support and configuration differences.

Linux 6.18 has a dedicated `ov5645` driver, enabled as a module in the release kernel and present in the release module archive. `mise run build-camera-ov5645` builds a temporary version with a Mirror-specific patch that matches the existing OV5640 DT compatible, uses the existing supply phandle names, and drives GPIO7 as an active-high enable. The driver initializes sensor registers before verifying the chip ID and uses existing borrowed supply mappings without changing voltage settings. The candidate `build/camera-ov5645.DmSlYCCR/ov5645.ko` has SHA-256 `6426a32546bef00dea6acb27dbd56ddb7654930b4f76d109d5598abda1493973`; its architecture, vermagic and undefined-symbol names match the release OV5645 module, but the build lacks the full kernel Module.symvers and ABI safety is not established. `mise run test-camera-ov5645 -- --check` is local only; the live test temporarily stops camhub, loads the candidate, prints binding and media topology, and attempts to restore the prior service state. This probe-only test does not verify frames. The existing `camhub.sh` and `camset.sh` explicitly match `ov5640`, so a successful OV5645 bind alone will not make the service work without a separate camera pipeline change.

The user ran the OV5645 test: it bound to `2-003c`, logged `OV5645 detected`, and appeared as a sensor in `/dev/media0`, with its link to the MIPI CSI receiver initially disabled. No frames were tested. Cleanup initially failed because `rmmod ov5645` returned in-use; camhub remained stopped. The user then unbound `2-003c` from the OV5645 driver, successfully removed the module, restarted camhub (reported active), and verified the unchanged original OV5640 module SHA-256. The test script now attempts to unbind this exact driver before removal, but the updated cleanup has not yet been run on the MIRROR.

The user subsequently ran `mise run test-camera-ov5645-capture`: the driver bound, the sensor-to-receiver link and 1920x1080 UYVY pipeline were configured, and `v4l2-ctl` returned success with 15 frame markers to `/dev/null`. Frame contents were not inspected. The kernel also reported `Lost Frame Start Error 0 events: 349` and `CRC Error events: 413`, so valid or reliable image capture has not been established. The updated cleanup successfully unbound the sensor, removed the test module, verified the original module state and file hash, and restarted camhub. The capture path does not persist after cleanup.

`mise run prepare-ov5645-dtb` creates a local stock-driver DTB candidate `build/ov5645-persistent/imx8mm-mirror-ov5645.dtb`, SHA-256 `ac1bb195a5b86b39f238c4ee3e6a87ade4247378b46fcf7b9e65a98d3aaf5ae8`, by changing the compatible string, GPIO property name, and supply property names while retaining their existing phandles, pin groups, polarities and clock. `mise run prepare-ov5645-camhub` prepares sensor-aware `camhub.sh` and `camset.sh` candidates in the same directory, retaining OV5640 support and avoiding frame-interval configuration unsupported by OV5645. Both scripts pass local shell syntax checks and the DTB passes a round-trip check. The stock OV5645 driver's initial GPIO request differs from the tested module (initial active-high enable vs initial low), and the stock driver plus new DTB and service scripts have not been tested together. No installer or rollback task for these candidates has been validated; do not deploy them yet. No MIRROR files were changed while preparing the candidates.

`mise run install-ov5645` and `mise run restore-ov5645` now provide install and rollback procedures, with local `--check` modes. The installer checks the release OV5645 module and original file hashes, makes and verifies backups of the DTB and both camera scripts under `/home/mirror/mirror-ov5645-recovery.bak`, and verifies replacements. The files are `original.dtb`, `camhub.sh`, and `camset.sh`; only the directory has the `.bak` suffix. The original installation used `/var/lib/mirror-ov5645-recovery`; the backups were subsequently relocated, and both install and restore now use the home-directory path. The restore procedure accepts only known original or candidate files, allowing recovery from a partially applied install without overwriting unrelated changes. Both operations require typed confirmation, print commands, and do not reboot. Shell syntax and local check modes have passed; neither live installer nor restore has been run, and USB/PROG1 file recovery remains untested end-to-end. If an operation fails, do not reboot until its state is understood.

The user subsequently ran `mise run install-ov5645`: all original preflight and stock module checks passed, the three recovery copies were verified, the candidate DTB and camera scripts were installed and verified, and the boot partition unmounted successfully. No reboot was issued by the installer. The new configuration is not active until reboot and has not yet been validated after reboot. The live restore task and USB/PROG1 file recovery remain untested.
