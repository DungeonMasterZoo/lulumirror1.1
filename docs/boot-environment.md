# Boot environment and installation

> This is a chronological research record. Statements about status and untested steps describe the time they were written, not necessarily the current state. Read the later entries and the [project overview](../README.md) before acting.

## Offline environment investigation

`mise run inspect-backup-env -- --check` checks the local backup path and size. `mise run inspect-backup-env` scans the user-area backup read-only for possible sector-aligned CRC-valid U-Boot environments with common sizes and headers. It prints offsets, not environment values. A match does not establish that stock U-Boot uses it; a miss does not rule out another format or a separate hardware partition. It never contacts the MIRROR or writes an environment.

On this MIRROR's verified user-area image, the scan returned zero candidates. This does not establish where stock U-Boot would save an environment, or even whether an environment has previously been saved. The extracted stock U-Boot is from a reference image, not verified as this device's exact binary; it contains fastboot and saveenv strings, which alone do not establish USB command support or the persistent environment backend.

Further offline analysis of the reference U-Boot against the NXP source suggests its MMC environment uses a 4096-byte record and a fallback offset of `0x400000`, subject to device-tree overrides and device selection. The 4096 bytes at that offset in this MIRROR's user-area backup are all zero, with no valid CRC. This is only a lead: an empty region does not show which hardware partition stock U-Boot uses, whether the device's actual bootloader matches the reference, or that it will read an environment written there. The reference binary does not contain the obvious `UCmd`/`ACmd` strings, so its fastboot command support is unproven. No environment was written.

`mise run probe-reference-boot0 -- --check` previews a USB-only boot0 comparison. The untested live task RAM-boots the experimental fastboot U-Boot, selects eMMC hardware partition 1, reads 4 MiB into RAM, compares against the first 4 MiB of the reference boot0 image, and attempts to select the user area afterward. It issues no block write or `saveenv`, but selection changes eMMC partition-access bits, and a failure can leave boot0 selected until power cycling or another selection. RAM placement and output are not verified; a successful UUU acknowledgment alone does not prove the comparison. It requires a fresh SDP boot and does not itself establish persistent environment behavior.

The live comparison reported all 4,194,304 bytes equal, and then reported `mmc2(part 0) is current device`. Subject to the RAM transfer and comparison behaving as intended, this matches the actual boot0 content to the reference. It does not independently prove which persistent environment is selected at normal boot or test an environment write.

`mise run prepare-usb-boot-test` creates a local CRC-valid 4 KiB candidate with the reference's compiled default variables and `bootcmd=ums 0 mmc 2`. `mise run write-usb-boot-test -- --check` checks only that candidate. The live `mise run write-usb-boot-test -- diskN` is a **persistent write**, not a dry run: it checks the external disk, MIRROR GPT identities, unmounted partitions, backed-up original bytes, current bytes and a typed confirmation before writing 4 KiB at user-area byte offset `0x400000`, then reads it back. A normal boot test remains unproven. If successful, stock U-Boot could expose writable UMS on each normal boot until the setting is changed or restored. Do not repeat or reboot on a write/readback failure without investigation.

With user approval the test environment was written to disk5 and read back unchanged. The original 4 KiB in the verified user-area backup were zero. Whether stock U-Boot actually loads it on normal boot remains untested; no LemonadeMirror partitions have been flashed.

The user subsequently power-cycled with PROG1 removed and confirmed that the USB disk appeared without the RAM-boot task. `diskutil` showed a 15.7 GB external `UMS disk 0` with the expected layout. This supports that stock U-Boot loaded the persistent test environment. Changing it to the final LemonadeMirror boot command remains a separate persistent write.

The user then ran the upstream installer; it reported successful writes and read-back verification of `boot_b` and `userdata`. `mise run set-lemonade-boot -- --check` validates the locally generated final environment without touching hardware. The live `mise run set-lemonade-boot -- diskN` checks the disk and the exact previously tested USB environment, asks for confirmation, replaces only the boot command, writes the 4 KiB environment and reads it back. It is a persistent write. Do not power-cycle on a write or read-back error without investigation.

The user subsequently ran `mise run set-lemonade-boot -- disk5`; it wrote and read back the expected environment SHA-256 `9b5ec774a15dc62effd7f5623c7f093bc7ac47f94cf8f64b2ee135f27c1c5368`. Linux boot and SSH succeeded; the camera investigation is below. The installer was given `America/Los Angeles`, which is not the standard `America/Los_Angeles` zone name and can be corrected after login.
